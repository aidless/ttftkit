# 缺陷分级与根因归档

性能测试岗的第 4 条职责：跟踪问题、分级、归因、沉淀知识库。模板在这里。本仓库没有 `defects/` 目录，也没有已归档的缺陷条目。

## 1. 分级

| 级别 | 判据（满足任一） | 响应 |
| --- | --- | --- |
| S0 阻塞 | 服务不可用；正确性错误（乱码、截断、错 token）；线上已在恶化 | 立即回滚/切流，2 小时内给根因初判 |
| S1 严重 | 违反已发布的准入标准；p95 退化 > 50%；错误率 > 1%；显存随时间单调上涨 | 当个迭代内修复，阻止发布 |
| S2 一般 | 可测的性能退化（10%~50%）；特定配置/输入才触发；稳定性抖动上升 | 排期修复，记录基线 |
| S3 轻微 | 指标体系/文档/可观测性缺口；不影响当前发布 | 进 backlog |

分级看**影响 + 是否已在线上**，不看「改起来难不难」。修改难度是排期问题，不是严重性问题。

## 2. 归档模板

下面的 DEF-0001 是格式样例。里面的毫秒数和机型是编的，不是本仓库的测量，根因一栏也是空的。

```markdown
## DEF-0001 <一句话现象>

- 级别：S1
- 发现时间：2026-10-31
- 影响版本：vllm 0.6.3 + rtx4090 profile / 8 并发
- 现象：TTFT p95 从 210ms 涨到 690ms，p50 基本不变
- 复现：ttftkit run --requests 64 --concurrency 32 --max-tokens 512（脚本见 scripts/repro-def-0001.sh）
- 判据：gate/policy.json 的 ttft_ms.p95 上限 400 → exit 1
- 根因：<待填：先假设后验证，验证方式写在这里>
- 验证：<改了哪一行/哪个参数后，哪个指标回到多少>
- 回归用例：<新增的测试或 CI 任务，保证同类问题能被抓住>
- 关联：<commit / issue / PR 链接>
```

**根因未验证时写「待填」，不许写推测当结论。** 「可能是显存碎片」不是根因；「把 `gpu_memory_utilization` 从 0.95 降到 0.85 后 p95 回到 215ms」才是。

## 3. 归因方法（按成本从低到高）

1. **分层定位**：先看是 TTFT 涨还是 decode 涨。TTFT 涨 → prefill/排队/连接；decode 涨 → 显存带宽、批大小、降频。
2. **对照组**：同模型同并发，换 `max_tokens`、换输入长度、换并发，看哪个维度触发。
3. **时间维度**：`degradation_ratio` > 1.2 说明「跑久了变慢」，优先怀疑显存/KV 碎片/热降频。
4. **引擎指标**：vLLM 的 `vllm:gpu_cache_usage_perc`、`vllm:num_requests_waiting`；SGLang 的 queue 指标。
5. **Profiler**：`nsys profile` / `torch.profiler` / `py-spy dump`（卡住时看调用栈）。

## 4. 知识库约定

如果以后要归档，建议一条一个文件，文件名 `DEF-<序号>-<短横线关键词>.md`，索引放 `defects/README.md`。这个目录现在不存在。在有可复现命令和验证过的根因之前，不要建空档案充数。

写进知识库的最小要求：

- 可复现命令（能照抄跑起来）
- 判定它「好/坏」的阈值来源
- 根因的**验证方式**（不是推测）
- 防止复发的回归用例

## 5. 与门禁的关系

每修完一个 S0/S1，问一句：**下次同样的问题出现，现有门禁能拦住吗？** 拦不住就把判据补进 `policy.json` 或补一条测试。缺陷库的价值不在于记录了多少条，而在于让同类缺陷不再复发。
